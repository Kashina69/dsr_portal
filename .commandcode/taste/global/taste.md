# Global

- Prefers a two-tier separation of concerns for types and data: module-local types/data live in `src/app/<route>/<route>.types.ts` and `src/app/<route>/<route>.data.ts` (when consumed only within that route), while truly cross-module shared types/data go in `src/types/<feature>.type.ts` and `src/data/<feature>.data.ts` (when used by 2+ routes). Types/data are never combined in a single file, and type/interface/enum definitions are never placed inside component code — always imported from a dedicated `.types.ts` file. Exception: global components in `src/components/global/` export their types directly from the flat `.tsx` component file (no separate types file, no barrel). Confidence: 0.85
- When scaffolding a new module/route, automatically creates the `<route>.types.ts` and `<route>.data.ts` files as part of the initial setup — no need to be reminded. This is part of the AI-first philosophy where conventions are proactively followed, not retroactively enforced. Confidence: 0.8
- When committing taste-only changes (updates to taste.md or category taste files), uses the format `taste update: <short summary>` as the subject line, followed by bullet points listing each new preference added. Regular code changes still use the standard type-tag format (`refactor:`, `fix:`, etc.). Confidence: 0.8
- Always runs `pnpm format` (Prettier) before committing to ensure all files are correctly formatted — not just linting/typechecking. Confidence: 0.9
- Skips the pre-commit pipeline ( pnpm test, build/lint commands) when the commit contains only markdown/doc files (.md) — commits directly without validation for markdown-only changes but run format to format the files. Confidence: 0.8
- Prefers precise commit scope discipline: inspect staged vs unstaged changes before committing, commit only the staged subset, and clearly communicate what was committed vs what remains behind. Confidence: 0.8
- Never auto-commit — only commit when explicitly told to do so. Confidence: 0.9
- Appends the trailer `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` to every git commit message (seen consistently across chore/docs/feat commits). Confidence: 0.85
- Prefers structured commit messages formatted with a type tag (`refactor:`, `fix:`, etc.) followed by a summary line, then bullet points of specific changes — and expects the agent to verify via `git diff` before composing the message. Confidence: 0.8
- Prefers importing all types from a module in a single import statement (e.g., `import type { TypeA, TypeB, TypeC } from "./path"`) rather than multiple separate type import lines. Confidence: 0.8
- Uses the design skill to guide UI decisions whenever building visual interfaces. Confidence: 0.8
- Prefers an incremental workflow: improve existing pages first before discussing or expanding to new features. Confidence: 0.8
- Prefers technical explanations in short bullet points with clear cause → effect structure (issue → fix → files changed), to quickly understand changes in the project. Confidence: 0.8
- Prefers keeping AI/project documentation (AGENTS.md, memory.md, component docs) updated as the project evolves — surgical updates to only the stale parts, not full rewrites, and excluding README. Confidence: 0.8
- Enforces max line limits per file and per function — splits code aggressively into smaller files, sub-components, hooks, and services to make the codebase easy for both humans and AI agents to understand, navigate, and debug following the best best practices mentioned above and followed in the project and follow projects folder structure. Confidence: 0.9
- Reusable/generic components (in `src/components/global/` and `src/components/ui/`) must remain free of domain-specific types, data imports, and business logic — all such concerns should be injected via props and generics from the consuming page. The reusable component should only know about its own generic interface, never import domain types or data files. Rationale: domain logic pollutes reusable components with unused and conditional content, making them harder to reuse across modules. Confidence: 0.9
- When asking for a diff between branches, wants the report broken down per file: file name, lines added/removed, and grouped by change status (files added, deleted, updated). Confidence: 0.7
- Plans and executes multi-file feature work in parallel "waves" of independent tasks (e.g., Wave 1 scaffold → Wave 2 shared UI + form route in parallel → Wave 3 remaining routes in parallel → Wave 4 docs), explicitly requiring that anything able to run concurrently never be executed sequentially — sub-plans must also specify parallel subagents for any concurrent parts, and execution must actually launch those parallel sub-agents rather than silently falling back to sequential work. If sub-agents fail (e.g., permission errors), retry with adjusted configuration (e.g., different prompt or background mode) and immediately surface the failure to the user — never abandon parallelization silently, and make it visible whether the work actually ran in parallel. Confidence: 0.95
- Prefers minimal implementation surface area: when asked to add a feature, first checks what existing infrastructure can be leveraged (e.g., already-present CSS variables, existing components, existing config) and only writes net-new code for what's genuinely missing, keeping the diff as small as possible. Confidence: 0.7
- Prefers theme transitions animated at the CSS variable level using `@property`-registered custom properties with `transition` on `:root`/`.dark`, rather than per-element transitions (`*`, `*::before`, `*::after { transition: ... }`) which cause a staggered cascade effect. All children reading `var(--<token>)` see the interpolated value simultaneously for a unified, non-laggy theme switch. Confidence: 0.9
- When implementing a cross-cutting UI feature (e.g., a theme toggle), applies it comprehensively to ALL relevant layouts/pages that need it — not just the primary route being worked on. Expects the agent to proactively survey every layout/header in the app and add the feature wherever appropriate, using the same shared component everywhere. Confidence: 0.7
- Prefers CSS utility classes (`dark:hidden`/`dark:block`) over JS conditional rendering for theme-dependent elements like toggle icons, to avoid hydration mismatches between server and client renders. Confidence: 0.8
- Follows a strict three-tier component placement convention: (1) `src/components/ui/` is ONLY for shadcn primitives (Button, Card, Badge, Input, etc.) and micro generic wrappers under 50 lines with zero domain coupling — a generic `StatusBadge` wrapping `Badge` with variant maps is acceptable, but anything coupled to a module type is not; (2) `src/components/global/` is for cross-module compositions used by 2+ separate route modules (e.g., `AppPagination` wrapping shadcn `Pagination`); (3) `src/app/<module>/components/` is for domain compositions used only within that module or its sub-routes (e.g., `DsrEntryBlock`, `WeeklyReportDetail`). Confidence: 0.95
- Generic naming for shared components: no module/feature prefixes in component names unless the file is module-scoped — e.g., `StatusBadge` not `DsrStatusBadge` (a module prefix plus coupling to the module's `DsrStatus` type was explicitly called out as wrong). Confidence: 0.9
- Names routes descriptively rather than minimally (e.g., `weekly-report/` over `weekly/`, to avoid future collisions) and keeps route segments matching their sidebar labels exactly (Add Report → `/add`, Sent Report → `/sent`). Confidence: 0.7
- Structures mock/static data to mirror the `.types.ts` shapes exactly, so a future database integration only replaces the service/data layer without touching consumers. Confidence: 0.8
- Writes implementation plans in a rigorous structured format: opens with a "read before starting" context file list (AGENTS.md, PROJECT.md, memory.md, relevant types/data/shared component files), a "Current State (do NOT redo these)" section, per-task specs with exact file paths and code snippets, a wave-based parallelization strategy, and closes with a checkbox verification checklist. Architectural decisions carry explicit rationale ("Why X not Y?"), proposed changes are tagged [NEW]/[MODIFY] per file, and the verification plan names exact commands (typecheck/lint/build) plus manual UI checks. Confidence: 0.85
- Before implementing a plan, validates the plan's "current state" claims against what is actually on disk — reads the files, checks off what's truly done, and treats already-completed tasks as no-ops (reporting "zero changes needed" with evidence) rather than blindly re-implementing them. Confidence: 0.8
- Expects new features to mirror the closest existing analogous implementation in the codebase: study the sibling route/pattern first, then copy its structure, layout, and logic exactly, adapting only naming (e.g., weekly-report routes mirror the dsr routes; sidebar group mirrors the DSR group's JSX). Confidence: 0.8
- Treats the todo list as a contract for "done": when wrapping up, expects all todos marked completed, the full verification suite re-run (`pnpm typecheck`, `pnpm lint`, `pnpm build`), and completion reported with concrete evidence (error counts, route counts, file inventories) — not a bare claim of done. Confidence: 0.7
- When fixing lint errors (e.g., unused imports), only addresses the specific lint issue — does not delete the associated UI content or page sections that the import belonged to. An unused import doesn't mean the content it serves is unwanted; if removing the import would orphan a UI section, either restore the section or ask before deleting. Confidence: 0.8
- When writing generic reusable components/hooks that accept data `T` and index into it by string keys (e.g., `row[key]`), avoids constraining `T extends Record<string, unknown>` because TypeScript interfaces lack implicit index signatures and will be rejected at type-check time. Instead uses a looser constraint (`T` alone, or `T extends { id: string }` when an ID field is required) and casts to `Record<string, unknown>` internally where indexed access is performed. Confidence: 0.8
- For global reusable components in `src/components/global/`, prefers a self-contained subfolder with barrel export: `<ComponentName>/<component-name>.types.ts` (types), `<component-name>.data.ts` (demo/mock data), `<ComponentName>.tsx` (component), and `index.ts` that re-exports the component, types, and data from a single barrel. Consumers import from `@/components/global/<ComponentName>` which resolves to the barrel — no separate `src/types/` or `src/data/` indirection for component-owned concerns. Confidence: 0.2
- For global components in `src/components/global/`, prefers flat `.tsx` files ONLY — no subdirectories, no barrel `index.ts`, no nested type/data files. The component file itself exports the component and its types. Data and type re-exports belong in the consuming route's `data/` and `types/` subdirectories (e.g., `app/components/data/` and `app/components/types/`) with barrel `index.ts` files. Global = flat, self-contained component files; route-level concerns (demo data, type re-exports) live under the route. Confidence: 0.9
